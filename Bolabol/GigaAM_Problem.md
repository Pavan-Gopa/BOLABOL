Проблема
========

В текущей реализации GigaAM присутствует комментарий примерно следующего смысла:

    Split by VAD / chunks <= 30s

Однако фактическая реализация режет аудио механически на фиксированные чанки примерно по 30 секунд.

Это создаёт реальный риск разрезания слова/фонемы непосредственно на границе чанков:

    chunk 1: ...начало сло-
    chunk 2: -ва...

Каждый chunk затем транскрибируется независимо, поэтому модель может:

- потерять слово;
- продублировать его;
- исказить начало/конец слова;
- вставить неправильную пунктуацию;
- получить артефакт непосредственно около границы 30 секунд.

Текущие тесты также недостаточны: проверка одного только maxChunkSeconds == 30 не подтверждает корректность сегментации речи.

Цель
====

Реализовать для GigaAM нормальную speech-aware / VAD-aware сегментацию аудио с максимальной длительностью входного chunk <= 30 секунд.

Главная задача — стараться разрезать аудио по паузам / неречевым участкам, а не по произвольному номеру sample.

При этом реализация должна корректно работать и с длинной непрерывной речью, где подходящей паузы около 30-секундной границы нет.

Требуемое поведение
===================

Новая система chunking должна соблюдать следующие свойства.

A. Hard limit

Ни один audio chunk, передаваемый в GigaAM inference, не должен превышать 30 секунд.

Используй фактический sample rate, а не магическое количество samples там, где это можно сделать надёжнее.

B. Prefer speech boundaries

Если приближается максимальная длина chunk, необходимо искать подходящую границу по:

- VAD;
- silence;
- non-speech segment.

Предпочтительно заканчивать chunk на естественной паузе ДО 30 секунд.

Например:

    speech .............. pause .... speech
    0s                    27.4s       28s

лучше сделать cut около 27.4–28s, а не продолжать до ровно 30.000s.

C. Target duration

Не нужно постоянно пытаться набить каждый chunk ровно до 30 секунд.

Рекомендуемая рабочая зона может быть примерно 25–28 секунд, при этом:

    max = 30 seconds

Конкретные параметры выбери после анализа модели и существующего VAD.

Все threshold/window значения вынеси в понятные constants/configuration вместо scatter magic numbers.

D. Long continuous speech fallback

Обязательно обработай ситуацию:

человек непрерывно говорит >30 секунд и возле границы нет VAD silence.

Алгоритм не должен:

- зависать;
- создавать chunk >30 секунд;
- терять участок audio;
- создавать пустые chunks.

В этом случае реализуй безопасный fallback.

Предпочтительная стратегия:

1. сначала искать VAD boundary;
2. если подходящей VAD boundary нет — поискать наиболее безопасную low-energy boundary в небольшом окне перед hard limit;
3. если и это невозможно/ненадёжно — использовать hard boundary с небольшим overlap между соседними chunks.

Если используешь overlap, необходимо решить проблему дублирования результата.

Предпочтительно делать deduplication на уровне decoded token IDs:

    suffix(previousChunkTokens)
           vs
    prefix(currentChunkTokens)

и удалять максимально совпадающий разумный token prefix текущего chunk.

Не делай хрупкую deduplication только через сравнение готовых строк, если token-level решение доступно в текущем pipeline.

Не вводи overlap без механизма удаления дублей.

E. Audio coverage

Система должна гарантировать, что исходное аудио:

- не теряется между chunks;
- не получает случайных дыр;
- не меняет порядок;
- не выходит за исходные bounds.

При отсутствии overlap:

    end(chunk N) == start(chunk N+1)

При наличии overlap перекрытие должно быть контролируемым и явно отражено в реализации.

F. Short audio

Для audio <= безопасного лимита не должно возникать ненужной сегментации.

G. Empty / silence

Проверь поведение для:

- пустого audio;
- очень короткого audio;
- практически полной тишины;
- speech + длинная тишина;
- длинной речи без пауз.

Архитектура
===========

Не помещай всю новую логику внутрь огромной функции GigaAM transcription.

Вынеси segmentation/chunking в отдельную хорошо тестируемую abstraction/function/type.

Название должно отражать реальное поведение, например:

    makeSpeechAwareChunks(...)
    SpeechAwareAudioChunker
    VADAudioChunker

или другой подходящий вариант.

Существующий misleading comment "Split by VAD" должен соответствовать реальности либо быть заменён нормальным описанием алгоритма.

Желательно разделить:

    segmentation
    inference
    token merging

так, чтобы chunking можно было unit-test'ить БЕЗ загрузки настоящей GigaAM Core ML model.

Тесты
=====

Добавь полноценные automated tests.

Не ограничивайся проверкой:

    maxChunkSeconds == 30

Минимально нужны следующие сценарии.

TEST 1 — short audio

Например 10 секунд.

Ожидается один chunk.

TEST 2 — pause before boundary

Synthetic audio:

    speech до ~27s
    silence
    speech дальше

Ожидается cut около silence boundary, а НЕ ровно на 30s.

TEST 3 — word/speech crosses 30s

Создай synthetic waveform, в котором активный speech-like участок находится непосредственно вокруг отметки 30 секунд, но немного раньше существует подходящая pause.

Chunker должен выбрать предыдущую safe boundary и не резать активный speech-region ровно в 30s.

Это одна из главных regression tests данной задачи.

TEST 4 — continuous speech >30s

Например 45–60 секунд без VAD pause.

Проверь fallback:

- каждый chunk <=30s;
- весь audio покрыт;
- нет infinite loop;
- нет empty chunks.

TEST 5 — several minutes

Synthetic long stream с несколькими speech/silence sections.

Проверить последовательную segmentation и отсутствие потери samples.

TEST 6 — silence

Полностью silent input должен корректно обрабатываться.

TEST 7 — exact boundary

Audio длиной ровно около 30 секунд.

Не должно быть странного лишнего микрочанка из нескольких samples.

TEST 8 — overlap/dedup

Если выбран overlap fallback, отдельно протестировать token merge.

Например:

chunk A tokens:
    [10, 20, 30, 40]

chunk B tokens:
    [30, 40, 50, 60]

final:
    [10, 20, 30, 40, 50, 60]

Добавь также negative cases, чтобы случайно одинаковые короткие token sequences не приводили к чрезмерной дедупликации.

Тесты не должны зависеть от скачивания огромной модели из сети.

Используй deterministic synthetic input/mocks там, где это возможно.

Performance
===========

VAD-aware segmentation не должна заметно ухудшать realtime/user experience.

Избегай:

- многократного полного копирования огромных audio arrays;
- O(n²) проходов;
- повторного VAD анализа одного и того же audio без необходимости;
- лишних Core ML/model initializations.

Если возможно, VAD выполняется один раз, после чего его timestamps используются chunker'ом.

Если slicing Swift Array создаёт значительные копии, оцени возможность использования ranges/ArraySlice или другой существующей abstraction проекта.

Thread safety / concurrency существующего engine не ломать.

Документация
============

Добавь короткий комментарий в код, описывающий реальную стратегию:

    VAD boundary
        ↓
    low-energy fallback
        ↓

если именно такая стратегия будет реализована.

GigaAM имеет ограничение на размер audio window, но hard fixed-size slicing может разрезать речь посередине слова.

Acceptance Criteria
===================

Работа считается законченной только если одновременно выполнено следующее:

- GigaAM больше не режет audio исключительно механически каждые 30 секунд;
- используется speech/VAD-aware boundary detection;
- ни один inference chunk не превышает установленный максимум;
- длинная непрерывная речь имеет безопасный fallback;
- между chunks не теряется audio;
- overlap, если он используется, не создаёт дублирующий transcription;
- chunking вынесен в тестируемую логику;
- добавлены regression tests для boundary cases;
- существующие релевантные tests проходят;
- нет новых ненужных dependencies;
- нет unrelated изменений.
