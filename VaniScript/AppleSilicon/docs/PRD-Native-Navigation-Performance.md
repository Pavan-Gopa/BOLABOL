# PRD — Молниеносная навигация по чанкам и сессиям в нативной VaniScript (Apple Silicon)

**Статус:** черновик для передачи кодовой модели
**Автор постановки:** диагностика по коду (Electron-версия `VaniScript/` vs нативная `VaniScriptAppleSilicon/`)
**Цель документа:** дать кодовой модели точные корневые причины и конкретные задачи, чтобы открытие чанка, «Approve & Next» и переход между сессиями стали мгновенными — как в Electron.

> Важно про достоверность: причины ниже выведены из чтения кода обеих версий, без запуска приложения и без профайла. Поэтому: **первая задача исполнителя — снять профиль (Instruments → Time Profiler + os_signpost) и подтвердить, какая из причин доминирует.** Гипотезы проранжированы по вероятности с метками `[высокая]/[средняя]/[низкая]`. Архитектурные факты (что и где в коде) — проверены и помечены `[факт]`.

> **Уточнение сценария (приоритетный кейс).** Торможение воспроизводится на **уже готовой импортированной сессии**: все чанки `.done` (сделаны в Electron, импортированы в нативную версию). Открытие любого чанка (например 5-го), переход к ранее открытому (3-му), и даже кнопка **Previous** — каждый раз долгая загрузка. Это **не** про запуск ASR/MT. Значит доминанта — в горячем пути навигации по **готовым** чанкам (см. P0 ниже), а причины P1/P2 (модель/конвейер) к этому кейсу **не относятся** — они срабатывают только для ещё не обработанных чанков.

## 0. TL;DR — что чинить в первую очередь

> Порядок исправлен под приоритетный кейс (готовая импортированная сессия, навигация туда-обратно).

1. **На КАЖДУЮ навигацию по готовому чанку заново прогоняется весь глоссарий.** `[высокая]` — **главный подозреваемый для вашего кейса.** `selectChunkIndex/moveChunk/openProject/Previous` → `processCurrentChunkIfNeeded` → `applyGlossaryEntriesToWorkflow(currentChunkOnly:true)`. Внутри для **каждой** из ~112 записей стартового глоссария (× несколько вариантов) **компилируется новый `NSRegularExpression`** и сканируются `original`, все `originalCues`, 4 поля `originalFormats`, `translated`, 4 поля `translatedFormats`, и **для каждого языка** в `translationsByLanguage` — текст + cue + 4 формата. Импортированный готовый проект несёт все эти форматы и языки → **тысячи компиляций регэкспов на главном потоке на один переход**, и всё это выбрасывается, если замен нет. → **Не применять глоссарий на навигации. Применять один раз (при импорте/обработке/правке глоссария), результат сохранять; навигация — только чтение. Плюс кэшировать скомпилированные регэкспы и делать ранний выход.**
2. **Тяжёлый рендер ревью: по одному `NSTextView` на каждую реплику + караоке-подсветка поиском подстрок ~10 Гц.** `[средняя-высокая]` При смене чанка все `NSTextView` пересоздаются; подсветка пересчитывается перебором слов по всему тексту. → **Предрассчитать диапазоны слов один раз, обновлять только дельту, переиспользовать вью.**
3. **На каждое сохранение пересериализуется весь список проектов.** `[средняя]` `saveCurrentProject` кодирует в JSON *все* проекты. На навигации по готовым чанкам срабатывает только если глоссарий что-то заменил (после фикса №1 — почти никогда), но как фоновый налог важен. → **Инкрементальное/отложенное сохранение только активного проекта.**
4. **(Только для НЕготовых чанков) Холодная загрузка модели на каждый чанк без кэша + навигация связана с инлайн-обработкой.** `[высокая для своего кейса]` `WhisperKit(config)` создаётся заново и `unloadModels()` после каждого чанка; нет префетча. К приоритетному кейсу (всё `.done`) **не относится**, но критично для обычного прохода новой сессии. → **Тёплый кэш моделей + фоновая очередь с префетчем.**

Причина 1 объясняет торможение навигации по **готовым** чанкам (включая Previous). Причина 2 — почему «режим караоке» ощущается зависшим и почему открытие готового чанка дорогое. Причина 4 — про «Approve & Next» с реальной обработкой новых чанков (отдельный кейс).

## 1. Контекст и наблюдаемая проблема

Две реализации одного продукта живут в одной папке:

- `VaniScript/` — **Electron + React/TypeScript**. Навигация по чанкам и переход между сессиями — мгновенные. Эталон UX.
- `VaniScriptAppleSilicon/` — **нативный SwiftUI / Swift Package** (WhisperKit/Core ML для ASR, MLX для перевода). Цель оптимизации.

**Симптомы в нативной версии (со слов пользователя):**
- После импорта проекта открытие чанка (обычно первого, для проверки караоке) занимает «колоссальное время», ощущается как зависание.
- «Approve & Next» — долгий спиннер, «крутится».
- Открытие сайдбара сессий и переключение чанк→чанк внутри сессии, либо переход в другую сессию кликом по её чанку — «дикое торможение».

**Целевое поведение:** открытие готового чанка и переход между сессиями неотличимы по скорости от Electron (десятки миллисекунд, без экрана `.processing`, без спиннера).

## 2. Архитектурный диагноз: почему Electron мгновенный, а Native висит

| Аспект | Electron (`VaniScript/`) — быстро | Native (`VaniScriptAppleSilicon/`) — медленно |
|---|---|---|
| Навигация по чанку | Смена `currentChunkIndex` → рендер двух `<textarea>`. Никакой обработки. `[факт]` `src/components/ChunkReview.tsx` | `selectChunkIndex/moveChunk/approveAndAdvance/openProject` → `processCurrentChunkIfNeeded()` `[факт]` `Stores/WorkflowStore.swift:507,497,517,1964,2007` |
| Обработка чанка | Фоновая очередь, статусы `queued→…→ready`, **префетч следующего** `[факт]` `src/services/chunk-queue.ts:nextPrefetchIndex` | Инлайн в момент открытия: экран `.processing`, полный ASR+MT `[факт]` `WorkflowStore.swift:2478` → `NativeProcessingPipeline.processCurrentChunk` |
| Модель | (cloud Gemini / резидентный llama.cpp-рантайм) | **Создаётся заново и выгружается на каждый чанк** `[факт]` `NativeProcessingPipeline.swift:349 loadWhisperKit`, `:132 unloadModels()` |
| Аудио в ревью | `<audio controls src=file://…>` — ленивое, силами ОС `[факт]` `ChunkReview.tsx:49` | `AVPlayer` создаётся лениво при Play, переиспользуется `[факт]` `WorkflowStore.swift:1467` (это ок) |
| Караоке | лёгкий DOM/textarea | один `NSTextView` на реплику + пересчёт подсветки ~10 Гц `[факт]` `ReviewWorkspaceView.swift:1407,1460,1473` |
| Персистентность | `localStorage`, инкрементально `[факт]` `src/services/storage.ts` | пересериализация **всего** списка проектов на каждое сохранение `[факт]` `WorkflowStore.swift:2245→2273`, `ProjectDiskStore.swift` |

Вывод: в Electron «открыть чанк» — это операция чтения готового состояния. В нативной версии «открыть чанк» нередко означает «загрузить модель и заново всё посчитать», а отрисовка готового чанка дороже из-за караоке-вью и сериализации. Лечим обе стороны.

## 3. Корневые причины

### P0. Глоссарий заново применяется к чанку на КАЖДУЮ навигацию `[высокая]` — доминанта для «готовой сессии»

**Где:** `Sources/VaniScript/Stores/WorkflowStore.swift` + `VaniScriptCore/GlossaryTextRewriter.swift`
- Горячий путь навигации по готовому чанку: `selectChunkIndex` (507) / `moveChunk` (497) / Previous (та же `moveChunk(delta:-1)`) / `openProject` (1949) → `processCurrentChunkIfNeeded` (2478). В ветке `chunk.status == .done` вызывается `applyGlossaryEntriesToWorkflow(workflow.settings.glossary, currentChunkOnly: true)` (стр. 2484). Дополнительно тот же вызов в `openProject` (стр. 2000) — **двойное** применение при открытии.
- `applyGlossaryEntry` (стр. 2356) на один чанк прогоняет **каждую** запись глоссария через `GlossaryTextRewriter.apply` по: `chunk.original`; всем `chunk.originalCues`; 4 полям `originalFormats` (txt/srt/vtt/markdown, стр. 2376/2431); `chunk.translated`; 4 полям `translatedFormats`; и по **каждому** языку в `chunk.translationsByLanguage` — `variant.text` + все `variant.cues` + 4 `variant.formats` (стр. 2390–2423).
- `GlossaryTextRewriter.apply` (стр. 19): для каждого варианта записи **компилирует новый `NSRegularExpression`** (стр. 29–30: `try? NSRegularExpression(pattern:...)`), затем `matches` + `stringByReplacingMatches`.
- Объём: стартовый глоссарий `StarterGlossary.entries` ≈ **112 записей**, у каждой несколько вариантов (`expandedVariants`, стр. 106).

**Почему медленно:** на один переход к готовому чанку получается порядка `112 записей × ~3 варианта × (original + N cue + 4 формата + translated + 4 формата + языки×(text + M cue + 4 формата))` **компиляций регэкспа и полных сканов строк на главном потоке**. Импортированный из Electron «полностью готовый» проект несёт максимум данных (заполнены и `*Formats`, и `translationsByLanguage` с cue и форматами) → это легко тысячи компиляций ICU-регэкспа на каждый переход. Компиляция `NSRegularExpression` дорогая; делается она заново каждый раз и **выбрасывается, если замен нет** (`total == 0` → результат не сохраняется, но вся работа уже выполнена).

**Почему именно это объясняет ваш кейс:** срабатывает на **любой** навигации между **готовыми** чанками — открытие 5-го, переход к 3-му, Previous — независимо от содержимого чанка и от того, нужна ли реально замена. Не зависит от моделей и обработки. Идеально совпадает с «каждый раз торможение, даже Previous».

**Доказательство:** `processCurrentChunkIfNeeded` (2478) безусловно зовёт `applyGlossaryEntriesToWorkflow` в `.done`-ветке; `GlossaryTextRewriter.apply` компилирует регэксп в цикле по вариантам (GlossaryTextRewriter.swift:28–30).

**Замечание про cue:** восстановление cue (`reconstructCues`/`reconstructCuesFromTimestampedText`) выполняется один раз при открытии в `normalizeTranslationArchive` (`SessionModels.swift:849`) и кэшируется в `chunks[*].originalCues`/`variant.cues` — т.е. это разовая стоимость открытия, **не** per-navigation. Не путать с P0.

### P1. Холодная загрузка модели на каждый чанк, выгрузка между чанками `[высокая, но только для НЕготовых чанков]`

**Где:** `Sources/VaniScript/Services/NativeProcessingPipeline.swift`
- `processCurrentChunk` (стр. 11) на каждый вызов: `loadWhisperKit(model:)` (стр. 85) → транскрипция → `await pipeline.unloadModels()` (стр. 132) → загрузка MLX-движка перевода → перевод.
- `loadWhisperKit` (стр. 349): `try await WhisperKit(config)` с `prewarm: false, load: true` — **новый экземпляр каждый раз**, без кэша и без прогрева.

**Почему медленно:** инициализация WhisperKit/Core ML (компиляция/загрузка `.mlmodelc`, аллокация ANE/GPU) — это секунды, для large-v3 — десятки секунд при первом обращении. Поскольку модель выгружается после каждого чанка, **каждый** переход к необработанному чанку платит полную холодную загрузку заново. То же для MLX-модели перевода.

**Доказательство:** связка `loadWhisperKit (новый WhisperKit) … unloadModels()` внутри обработки одного чанка, без хранения экземпляра в поле сервиса.

### P2. Навигация связана с инлайн-обработкой; нет фоновой очереди и префетча `[высокая]`

**Где:** `Sources/VaniScript/Stores/WorkflowStore.swift`
- `processCurrentChunkIfNeeded(force:)` (стр. 2478): если `chunk.status != .done`, ставит `workflow.screen = .processing` и запускает `processCurrentSession()` → `processingPipeline.processCurrentChunk(...)`.
- Вызывается из `selectChunkIndex` (507), `moveChunk` (504), `approveAndAdvance` (531), `openProject` (1964, 2007).

**Почему медленно:** при движении вперёд по сессии (а «Approve & Next» — это почти всегда переход к ещё не обработанному чанку) каждое нажатие = полный конвейер на переднем плане со спиннером. Нет предварительной подготовки следующего чанка во время того, как пользователь читает текущий.

**Контраст-эталон:** `src/services/chunk-queue.ts` — конечный автомат статусов и `nextPrefetchIndex(state)` (стр. 52), который заранее готовит следующий чанк; UI (`ChunkReview.tsx`) лишь читает `chunk.status`.

### P3. Караоке: пересчёт подсветки ~10 Гц поиском подстрок + по `NSTextView` на реплику `[средняя-высокая]`

**Где:** `Sources/VaniScript/Views/ReviewWorkspaceView.swift`
- `SelectionAwareCueTextView: NSViewRepresentable` (стр. 1407) — отдельный `NSScrollView + NSTextView` **на каждую реплику** (cue). При смене чанка все они пересоздаются.
- `updateNSView` (стр. 1460) вызывается на каждое изменение `playbackTime` (тикает 10 Гц через периодический обсёрвер `WorkflowStore.swift:1493`, интервал 0.10 c) → `applyKaraokeAttributes` (стр. 1473).
- `applyKaraokeAttributes`: сбрасывает атрибуты по всему диапазону, затем в цикле по **всем** словам делает `textView.string.range(of: cleanedWord, options:[.caseInsensitive,.diacriticInsensitive])` (стр. 1511–1540).

**Почему медленно:** сложность ~O(числоСлов × длинаТекста) на каждый тик, для каждой активной реплики, плюс перестройка `NSAttributedString` и `needsDisplay`. При открытии чанка дополнительно — создание стопки `NSTextView` синхронно на главном потоке. Это и есть «караоке тормозит».

**Контраст:** Electron-ревью использует обычные `<textarea>` (`ChunkReview.tsx:72,87`); даже отдельный караоке-слой в Electron работает на лёгком DOM/CSS.

### P4. Полная пересериализация хранилища проектов на каждое сохранение + лишние пересчёты `[средняя]`

**Где:** `Sources/VaniScript/Stores/WorkflowStore.swift`, `Services/ProjectDiskStore.swift`
- `saveCurrentProject` (стр. 2245) → `persistProjects` (стр. 2273): `ProjectDiskStore.save(projects)` кодирует в JSON **весь** массив `projects` (все сессии, чанки, cue, слова, shorts-планы, выравнивания, кейфреймы) и пишет одним atomic-файлом. Вызывается на каждый `approveAndAdvance`, смену провайдера, применение глоссария и т. п.
- На главном потоке перед фоновым кодированием: `normalizeTranslationArchive()` + `ProjectArchive.sortedRecent(projects)` + переприсваивание `@Published var projects` (инвалидация SwiftUI, пересчёт `projectSummaries` (стр. 169) для всего списка).
- Двойной проход глоссария при открытии: `openProject` (стр. 2000) и затем `processCurrentChunkIfNeeded` (стр. 2484).
- `currentTranslationCues` (стр. 214) при пустых cue, но непустом тексте перевода вызывает `reconstructCues` → `splitTranslatedText` + `approximateWords` **на каждое чтение свойства** (а его читают несколько раз за рендер: стр. 264, 270, 313).

**Почему медленно:** даже при фоновом кодировании растут латентность копии большого графа и нагрузка на главный поток от `@Published`/`sortedRecent`. На больших библиотеках после импорта фоновое кодирование всего стора конкурирует с UI. Лишние пересчёты cue/глоссария добавляют миллисекунды на каждый рендер.

**Контраст:** Electron хранит настройки/usage в `localStorage` и состояние чанков инкрементально (`storage.ts`), не переписывая весь архив проектов на каждый клик.

### P5. После импорта может отсутствовать нарезанное аудио чанков `[низкая-средняя]`

**Где:** `WorkflowStore.swift:startPlayback` (стр. 1423): если файла чанка нет, выполняется `AudioChunkExporter.exportChunks(...)` из исходника на лету (стр. 1439).

**Почему важно:** не вызывает фриз самой навигации, но если караоке/воспроизведение стартует автоматически при открытии чанка импортированного проекта, пользователь увидит паузу на повторную нарезку. Учесть, чтобы «проверка караоке после импорта» не упиралась в это.

## 4. Целевая архитектура (target state)

1. **Резидентные движки.** ASR (WhisperKit) и MT (MLX) живут как долгоживущие акторы в памяти: загрузка один раз, прогрев, переиспользование между чанками и сессиями. Выгрузка — только по явному сигналу (смена модели, нехватка памяти, длительная неактивность), а не после каждого чанка.
2. **Навигация = чтение состояния.** Открытие/переключение чанка и переход между сессиями только меняют индекс и показывают уже готовый контент. Экран `.processing` появляется только когда контента реально нет.
3. **Фоновая очередь обработки с префетчем.** Сервис обрабатывает неготовые чанки в фоне, начиная с текущего и префетча следующего (по образцу `chunk-queue.ts`). UI подписан на статусы.
4. **Дешёвая отрисовка ревью/караоке.** Диапазоны слов предрассчитаны и закэшированы в модели cue; подсветка обновляет только дельту; число и пересоздание тяжёлых `NSTextView` минимизированы.
5. **Инкрементальная персистентность.** Сохраняется только активный проект, отложенно (debounce), вне главного потока, без переписывания всего архива на каждый клик.

## 5. Задачи для реализации

### R0 — Убрать применение глоссария из навигации (закрывает P0) `[приоритет 0 — делать первым для вашего кейса]`

Суть: применение глоссария — это **мутация контента**, а не часть рендера/навигации. Делать его один раз, а навигацию сделать чистым чтением.

- **Убрать `applyGlossaryEntriesToWorkflow` из горячего пути.** В `processCurrentChunkIfNeeded` (стр. 2484) и из второго прохода в `openProject` (стр. 2000) **не** применять глоссарий на каждое открытие/переключение/Previous.
- **Применять глоссарий по событию, а не по навигации:**
  1. при импорте проекта (один раз, в фоне, по всем чанкам);
  2. в конце обработки чанка в конвейере (там это уже частично есть — `applySourceGlossary`/`applyTranslationGlossary` в `NativeProcessingPipeline`);
  3. при изменении самого глоссария пользователем (тогда — пройти по затронутым чанкам в фоне).
  Результат сохранять в модель, чтобы повторное применение не требовалось.
- **Идемпотентность и ранний выход.** Хранить на чанке отметку «глоссарий версии X применён» (хеш/идентификатор набора глоссария). Если версия совпадает — мгновенно пропускать. Это исключает повторную работу даже при событийном применении.
- **Кэш скомпилированных регэкспов.** В `GlossaryTextRewriter` кэшировать `NSRegularExpression` по строке варианта (статический словарь/`NSCache`), а не компилировать в цикле (стр. 29–30). Сразу убирает основную стоимость, даже если где-то глоссарий всё же прогоняется.
- **Только в фоне.** Любое массовое применение глоссария — вне главного потока, с батч-сохранением (см. R4), без блокировки UI.

**Критерий:** переключение между готовыми чанками и Previous не вызывают ни одной компиляции регэкспа и ни одного прохода глоссария (подтверждается сигнпостами); время перехода — десятки мс.

### R1 — Тёплый кэш моделей (закрывает P1) `[приоритет 1]`

- В `NativeProcessingPipeline` (или в новом `ModelResidencyService`-акторе) хранить загруженные `WhisperKit` и MLX-движок в полях; ключ кэша — идентификатор/путь/вариант модели.
- `loadWhisperKit` → `ensureWhisperKit(model:)`: если в кэше тот же `model`, вернуть существующий экземпляр; иначе загрузить и сохранить. Включить `prewarm: true` при первом старте сессии.
- **Убрать `await pipeline.unloadModels()` после каждого чанка** (стр. 132). Выгрузка — только в явных случаях: смена выбранной модели, `newSession()` при необходимости, предупреждение о памяти (`os_proc`/`memoryPressure`), таймаут неактивности.
- Аналогично для MLX-движка перевода (один резидентный экземпляр на выбранную модель).
- Прогрев при входе в проект: после `openProject` запускать фоновую загрузку нужных моделей, чтобы первый чанк не ждал.

**Критерий:** второй и последующие чанки в сессии не платят загрузку модели; в логах одна загрузка на сессию (а не на чанк).

### R2 — Развязать навигацию и обработку + префетч (закрывает P2) `[приоритет 1]`

- Ввести `ChunkProcessingQueue`-актор: статусы по образцу `chunk-queue.ts` (`queued/chunking/transcribing/translating/ready/failed`), методы `enqueue(index)`, `prefetchNext(after:)`.
- `selectChunkIndex/moveChunk/openProject`: **не вызывать тяжёлый конвейер синхронно**. Менять индекс, показывать готовый контент; если чанк не `ready` — лёгкий локальный индикатор в области панелей (не полноэкранный `.processing`), а очередь обрабатывает его в фоне.
- После показа чанка `N` — `prefetchNext(after: N)` (готовить `N+1`), как `nextPrefetchIndex`.
- `approveAndAdvance`: помечать approved, сдвигать индекс мгновенно; если следующий уже `ready` (благодаря префетчу) — экран ревью открывается без ожидания.
- Сохранить экран `.processing` только для самого первого, ещё не нарезанного запуска сессии.

**Критерий:** «Approve & Next» к префетченному чанку < 200 мс; полноэкранный спиннер при обычной навигации не появляется.

### R3 — Ускорить караоке-подсветку и ревью-вью (закрывает P3) `[приоритет 2]`

- **Предрассчитать диапазоны слов один раз.** Для каждой cue заранее посчитать `[(NSRange, startSec, endSec)]` (при создании/изменении cue, не на каждый тик). Убрать `string.range(of:)`-поиск из горячего пути `applyKaraokeAttributes` (стр. 1511–1540).
- **Обновлять только дельту.** На тике playback менять атрибуты лишь у слова, которое стало/перестало быть активным (снять подсветку с предыдущего, поставить на текущее), не сбрасывая атрибуты всей реплики.
- **Тротлинг.** Совместить частоту обновления подсветки с реальной потребностью (по границам слов, а не безусловно 10 Гц); обновлять только активную/видимую реплику.
- **Переиспользование вью.** Не пересоздавать `NSTextView` на каждую смену чанка без нужды; рассмотреть единый `NSTextView` на панель с диапазонной подсветкой вместо одного вью на реплику, либо устойчивую идентичность вью при `ForEach`.
- Закэшировать `nsFont(...)` (стр. 1544) — не конструировать шрифт на каждый `updateNSView`.

**Критерий:** во время караоке-проигрывания главный поток не блокируется кадрами > 16 мс (Instruments), открытие готового чанка с караоке < 150 мс.

### R4 — Инкрементальная персистентность и убрать лишние пересчёты (закрывает P4) `[приоритет 2]`

- Хранить проекты по файлу на проект (или индекс + отдельные файлы), сохранять **только активный** проект. Минимум — отдельный «горячий» файл текущего проекта, периодически сливаемый в общий.
- Debounce сохранения (например, 300–500 мс, коалесцируя частые `saveCurrentProject`), на фоне; убрать тяжёлую работу с главного потока.
- Не переприсваивать весь `@Published var projects` на каждое сохранение; обновлять точечно, а `projectSummaries` мемоизировать (пересчёт только при реальном изменении набора/метаданных).
- Мемоизировать `reconstructCues` (кэш по ключу «язык + хеш текста перевода»), чтобы `currentTranslationCues` не пересобирался на каждое чтение; в идеале сохранять восстановленные cue в модель при первом расчёте.
- Убрать двойной проход глоссария при открытии: оставить один (в `openProject` **или** в `processCurrentChunkIfNeeded`, не оба).

**Критерий:** «Approve & Next» не вызывает кодирование всего архива; сохранение не растёт линейно с числом проектов в библиотеке.

### R5 — Гарантировать доступность аудио чанка после импорта (закрывает P5) `[приоритет 3]`

- При импорте проекта либо переносить нарезанные аудио-чанки в бандле, либо помечать чанки как «нужна ленивая нарезка» и нарезать в фоне (через очередь R2), не блокируя открытие/караоke.
- Не автозапускать воспроизведение до готовности аудио; показывать ненавязчивый статус «подготовка аудио».

## 6. Критерии приёмки (измеримые)

На репрезентативном проекте (например, ≥ 20 чанков, длинная исходная дорожка), сборка Release на Apple Silicon:

1. Открытие уже готового (`.done`) чанка из сайдбара: **< 150 мс** до интерактивного ревью.
2. Переключение чанк→чанк внутри сессии (готовые чанки): **< 150 мс**, без полноэкранного спиннера.
3. Переход в другую сессию кликом по её готовому чанку: **< 200 мс**.
4. «Approve & Next» к префетченному чанку: **< 200 мс** до ревью.
5. Загрузка ASR/MT-модели происходит **один раз на сессию**, а не на чанк (подтверждается логами/сигнпостами).
6. Караоке-проигрывание: нет зависаний главного потока (нет кадров > 16 мс в Time Profiler в течение типичной реплики).
7. Сохранение проекта не блокирует UI и не масштабируется с размером всей библиотеки проектов.

## 7. План профилирования и проверки (делать ПЕРВЫМ)

1. **Instruments → Time Profiler + os_signpost.** Расставить `os_signpost` (интервалы) вокруг: `loadWhisperKit`, `processCurrentChunk`, `applyKaraokeAttributes`, `persistProjects`/`ProjectArchive.encode`, и вокруг перехода в `openProject/selectChunkIndex`.
2. **Подтвердить доминанту.** Сценарии: (а) **открытие/переключение готовых чанков и Previous в импортированной сессии — приоритетный кейс**; (б) «Approve & Next» по необработанным чанкам; (в) переход между сессиями; (г) караоке-проигрывание. Сопоставить, где сидит главный поток.
   - Если время в `GlossaryTextRewriter.apply`/`NSRegularExpression(pattern:)`/`applyGlossaryEntry` → подтверждает **P0** (ожидаемая доминанта для кейса «готовая сессия»).
   - Если время в `applyKaraokeAttributes`/создании `NSTextView`/layout → **P3**.
   - Если время в `WhisperKit(...)`/Core ML load → **P1** (только на необработанных чанках).
   - Если экран уходит в `.processing` и время в `pipeline.transcribe` → **P2** (нет префетча/тёплой модели).
   - Если время в `JSONEncoder`/`ProjectArchive.encode`/`sortedRecent` → **P4**.

   Быстрая проверка P0 без Instruments: временно закомментировать `applyGlossaryEntriesToWorkflow(...)` в `processCurrentChunkIfNeeded` (стр. 2484) и в `openProject` (стр. 2000) и пройтись по готовым чанкам — если торможение исчезло, доминанта подтверждена.
3. **Регресс-замеры.** Зафиксировать тайминги по критериям §6 до и после каждого R-блока (микро-бенч на главном потоке: `CACurrentMediaTime()` вокруг перехода).
4. **Юнит/функц-тесты:** очередь обработки (статусы, префетч), мемоизация `reconstructCues`, инкрементальное сохранение (сохраняется только активный проект). Прогнать существующие тесты в `Tests/VaniScriptCoreTests/`.

## 8. Порядок внедрения

1. **R0** (убрать глоссарий из навигации) — **первым**: закрывает доминанту для готовой импортированной сессии (открытие/переключение/Previous), малый радиус изменений, эффект сразу.
2. **R3** (караоке/ревью-рендер) — убирает «караоке тормозит» и остаточную стоимость открытия готового чанка после R0.
3. **R1** (тёплый кэш моделей) — самый большой выигрыш на «Approve & Next»/движении вперёд по **новой** сессии с реальной обработкой.
4. **R2** (развязка навигации + префетч) — устраняет полноэкранный спиннер на необработанных чанках, делает навигацию «чтением».
5. **R4** (персистентность/пересчёты) — снимает фоновый налог, важен на больших библиотеках.
6. **R5** (аудио после импорта) — полировка сценария «проверить караоке сразу после импорта».

> Если нужен один минимальный коммит «чтобы перестало тормозить здесь и сейчас» — это **R0** (вынести глоссарий из `processCurrentChunkIfNeeded`/`openProject` + кэш регэкспов).

## 9. Риски и не-цели

- **Память.** Резидентные модели держат RAM/VRAM. Добавить реакцию на `memoryPressure` и выгрузку по таймауту неактивности; не держать одновременно несколько вариантов одной модели.
- **Корректность префетча.** Префетч не должен молча проглатывать ошибки чанка — статус `failed` обязан доходить до UI.
- **Параллелизм.** ASR и MT — тяжёлые; ограничить очередь одним активным заданием, чтобы префетч не конкурировал с обработкой текущего чанка за ANE/GPU.
- **Не-цели:** менять формат проектов на диске, переписывать ASR/MT-движки, трогать пайплайн рендера видео/Shorts. Только производительность навигации, караоке и персистентности.
